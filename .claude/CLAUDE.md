# 项目：ROSbot - STM32 下位机 + ROS 上位机

## 仓库结构
- firmware/ - STM32 工程，使用 keil + 标准库
- ros_ws/ - ROS 工程，在树莓派 4B 上使用 ROS Noetic + ubuntu20.04
- docs/ - 关键协议和决策记录，必须先读

## 工作规则

### 当你在 STM32 侧工作时
- 修改 `firmware/` 下的代码
- `firmware/` 下存在标准库函数，除非及其特殊的情况，不要进行任何库函数及系统级文件的修改，如需修改需要告知用户
- 如果改变通信协议（数据格式、波特率、帧结构），**必须** 更新 `docs/communication_protocol.md`
- 读取`docs/stm32_cfg.md` 获取STM32端的必要的硬件配置信息，包括MCU,电机,其他可能的传感器等
- 硬件相关的配置已固定,在排查问题时忽略硬件配置相关的选项（比如无法对引脚定义进行更改）
- 提交信息格式：`stm32: <描述>`

### 当你在 ROS 侧工作时
- 修改 `ros_ws/` 下的代码
- 读取 `docs/communication_protocol.md` 来理解数据格式
- 如果发现 STM32 的问题，在 `docs/debugging_guide.md` 中添加条目（格式：`[问题] 现象 -> 建议排查`）
- 提交信息格式：`ros: <描述>`

### 通用规则
- 每次对话开始时，执行 `git pull` 获取最新变更
- 每次修改完成后，执行 `git add -A && git commit -m "<格式>" && git push`
- 双端进行 `git add`时需要将`docs/update.md` 一并包含
- 当用户说“同步”时，执行 `git pull` 并重新读取 `docs/` 下的文档
- 不要更改任何 `docs/` 下带_cfg后缀的文件，此类配置文件只能由用户手动更改
- 无论处于哪个工作端，编写完代码后不要执行任何编译和烧录等操作，只需要告知用户，用户会手动进行编译并且将结果反馈
- 双端完成一次功能的更改时需要对 `docs/update.md` 进行更新，此文件内记录了目前实现的功能
- 双端代码风格统一
- `tools/` 下存放各类工具或脚本
- 尽量不在主函数中堆砌过多内容，重要逻辑单独拆分出文件
- 任何一个工作端不仅仅只完成自己的工作，也需要注意与另一端的沟通配合
